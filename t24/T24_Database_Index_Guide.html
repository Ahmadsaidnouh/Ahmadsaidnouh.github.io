T24 Database Index Creation Guide

Prepared by: Ahmad Said Nouh

How T24 stores its tables in Oracle, how TAFJ turns your JQL into SQL, and how to add an index that makes a slow selection fast and survives STANDARD.SELECTION rebuilds.

Scope: every command and SQL statement here is for the Oracle implementation of TAFJ. On other databases (SQL Server, PostgreSQL, H2) the commands and syntax differ, but the idea and the steps are the same.

1. How T24 stores a table: RECID + XMLRECORD

If you open any T24 table in Oracle, you won't find one column per field. Every T24 table has just two columns:

SQL> DESC FBNK_EB_EMK_BNPL_SETTLEMENT_RPT_DETS
 Name        Null?     Type
 ----------- --------- -------------
 RECID       NOT NULL  VARCHAR2(255)    <- the record @ID
 XMLRECORD             SYS.XMLTYPE      <- ALL the fields, as one XML document

Each field of the record lives inside the XML as an element called <cN>, where N is the field number from STANDARD.SELECTION (SYS.FIELD.NO). A multi-value field repeats the same element with an m attribute for each extra value.

Let's follow one record through the three ways you meet it:

① What Oracle stores

RECIDWF-0000000001937-BNPL|INS1

XMLRECORD

<row id="WF-...|INS1">
  <c1>20261102</c1>
  <c2>ACME STORES</c2>
  <c3>ACME01</c3>
  <c4>20261102-WF-...-BNPL</c4>
  <c7>refundAfterRma</c7>
  <c22>BNPL561146201758</c22>
  <c24>561146</c24>
  ...
</row>

② What you see in Browser

@IDWF-...|INS1 TRANSACTION.DATE02 NOV 2026 MERCHANT.NAMEACME STORES MERCHANT.CODEACME01 ORDER.ID20261102-WF-...-BNPL REFUND.STATUSrefundAfterRma SETTLEMENT.REFBNPL561146201758 MERCHANT.ID561146

③ How you query it in JQL

LIST FBNK.EB.EMK.BNPL.
  SETTLEMENT.RPT.DETS
  WITH ORDER.ID EQ
  "20261102-WF-...-BNPL"

You use the field name. T24 knows that ORDER.ID means c4 because STANDARD.SELECTION says so:

SYS.FIELD.NAMEORDER.IDSYS.FIELD.NO4SYS.SINGLE.MULTS

The same record three ways. Oracle sees one XML blob, Browser shows named fields, and JQL lets you filter by field name. The link between "ORDER.ID" and <c4> is the field number in STANDARD.SELECTION. (Sample values are illustrative.)

Key takeaway: Oracle doesn't know that a column called "ORDER.ID" exists. To Oracle, ORDER.ID is "the text inside <c4> in the XMLRECORD column". That's why indexing a T24 field takes a little more work than indexing a normal SQL column.

2. Why Temenos chose this design

The short answer is history and multi-values. T24 (originally Globus) was built on a MultiValue database: first UniVerse, then jBASE from around 2003. A single field in a MultiValue database can hold a list of values (multi-values), and each of those can hold its own list (sub-values). Think of OVERRIDE, INPUTTER or any associated multi-value group.

When Temenos added support for Oracle and other mainstream relational databases, it wrote a database driver that imitates the MultiValue behaviour inside the relational database. To store the multi-dimensional fields, it used XML. So every T24 table in Oracle has two columns: RECID for the record's key and XMLRECORD for the data.

XMLRECORD is created as XMLTYPE by default, but it can also be a BLOB or CLOB. TAFJ records which storage each table uses in its TAFJ_VOC file.

Why not a full relational schema (one column per field)?

ReasonWhat it means in practice
Multi-values and sub-valuesA field like OVERRIDE can have any number of values. A relational schema would need a child table for every multi-value field (hundreds of them), and joins on every read. In XML they are just repeated elements in the same record.
One application, many databasesThe same T24 code runs on Oracle, SQL Server, DB2, PostgreSQL, H2 and so on. A 2-column key/document table looks the same on all of them, so the application logic doesn't depend on the database.
Schema changes without DDLAdding a field, a local reference or a whole new application (EB.TABLE.DEFINITION / STANDARD.SELECTION) doesn't need an ALTER TABLE on a production database. The new field simply appears as a new <cN> in new records.
Record-at-a-time programming modelT24 code reads and writes whole records (F.READ/F.WRITE, or getRecord/write in Java). Fetching one document by key is exactly what this design is fastest at.

Temenos also added a multi-column option for specific tables that need very fast indexing. Multi-values are then stored in NVARCHAR columns. The trade-off is slower reads, because the record has to be rebuilt from all the columns, in exchange for faster indexing on single-value fields. It's a special-case setting, not the default.

The cost of this design: reading one record by @ID is very fast, because RECID is the primary key. Selecting by a field inside the XML (WITH ORDER.ID EQ ...) means Oracle has to open the XML of every row unless an index exists. On a table with hundreds of thousands of records, that is what turns a selection into minutes or hours. Indexes fix exactly this.

3. TAFJ, the isolation layer between JQL and SQL

We write JQL (SELECT … WITH …) in T24, and Java code calls DataAccess.selectRecords(...). Oracle doesn't understand JQL. TAFJ (Temenos Application Framework for Java) sits in between. It translates every JQL selection into SQL and sends that SQL to the database. At the end, everything we run is SQL.

T24 layer: Browser, enquiries, services, Java/L3 hooks
SELECT FBNK.EB.EMK.BNPL.SETTLEMENT.RPT.DETS WITH ORDER.ID EQ "X"
▼JQL
TAFJ: translates JQL to SQL, and field names to view columns
FBNK.EB.EMK.BNPL.SETTLEMENT.RPT.DETS → V_FBNK_EB_EMK_BNPL_SETTLEMENT_RPT_DETS; ORDER.ID → "ORDER_ID"
▼SQL
Default view V_FBNK_…: one column per field, each extracted from the XML
XMLCast(XMLQuery('/row/c4[position()=1]' PASSING a.XMLRECORD …)) "ORDER_ID"
▼reads
Physical table FBNK_…: RECID + XMLRECORD

Each layer only talks to the one below it. T24 never builds SQL itself, and Oracle never sees JQL.

Because of this layer:

  • T24 code stays the same whatever the database.
  • The performance of a selection is decided by Oracle, using the SQL that TAFJ generated. To make a selection faster, you have to look at that SQL, not the JQL.

4. What a view is, and the TAFJ default view

A view in one minute

A view is a saved SELECT statement with a name. It stores no data of its own. When you query a view, the database runs the saved SELECT underneath and gives you the result as if it were a table.

-- A view is just a named query
CREATE VIEW V_ACTIVE_CUSTOMERS AS
  SELECT ID, NAME FROM CUSTOMERS WHERE STATUS = 'ACTIVE';

-- Querying it...
SELECT NAME FROM V_ACTIVE_CUSTOMERS WHERE ID = 10;
-- ...really runs:  SELECT NAME FROM (SELECT ID, NAME FROM CUSTOMERS WHERE STATUS='ACTIVE') WHERE ID = 10;

The TAFJ default view

For every T24 table, TAFJ creates a default view called V_<table>. It turns the XML back into normal columns, one per STANDARD.SELECTION field, named after the field (dots become underscores). This view is the isolation layer from section 3: TAFJ runs every selection against this view, not against the table.

Physical table (what's stored)

RECIDXMLRECORD
WF-…|INS1<row><c1>…</c1><c4>ORD-A</c4>…</row>
WF-…|INS2<row><c1>…</c1><c4>ORD-A</c4>…</row>
WF-…|INS3<row><c1>…</c1><c4>ORD-B</c4>…</row>

Default view (what TAFJ queries)

RECIDTRANSACTION_DATEORDER_IDMERCHANT_ID…
WF-…|INS120261102ORD-A561146…
WF-…|INS220261102ORD-A561146…
WF-…|INS320261103ORD-B561146…

The view's ORDER_ID column isn't stored anywhere. Each time it is queried, Oracle extracts it from <c4> for every row.

This is the part of the real view script that defines ORDER_ID:

CREATE OR REPLACE FORCE EDITIONABLE VIEW "TXN_ADMIN"."V_FBNK_EB_EMK_BNPL_SETTLEMENT_RPT_DETS" (...) AS
  SELECT a.RECID, a.XMLRECORD "THE_RECORD", a.RECID "DEAL_NO"
  ,XMLCast(XMLQuery('/row/c1[position()=1]' PASSING a.XMLRECORD RETURNING CONTENT) AS VARCHAR(4000)) "TRANSACTION_DATE"
  ...
  ,XMLCast(XMLQuery('/row/c4[position()=1]' PASSING a.XMLRECORD RETURNING CONTENT) AS VARCHAR(4000)) "ORDER_ID"
  ...
FROM "FBNK_EB_EMK_BNPL_SETTLEMENT_RPT_DETS" a
Important: the view belongs to T24. When the table's STANDARD.SELECTION record is rebuilt, TAFJ regenerates the default view. Any manual edit to the view is lost. We confirmed this in SIT. Never fix performance by editing the view. Put the fix on the table, which is what the method below does.

5. Step 1: find your table's default view (JQL2SQL)

Before you can index anything, you need the exact SQL TAFJ runs for your table, and from it the name of the default view. DBTools can translate JQL to SQL for you.

Example: I want to index a field on AA.ARRANGEMENT.

  1. Log in to DBTools on the environment you're working in (SIT first).
  2. Run JQL2SQL followed by any JQL against your table. The field and value don't matter. Use any existing field as a dummy filter, because we only want to see how TAFJ translates the table name: 
    JQL2SQL COUNT FBNK.AA.ARRANGEMENT WITH CURRENCY EQ "SAR"
  3. Read the SQL it prints. You'll get something like: 
    SELECT COUNT(RECID) FROM "V_FBNK_AA_ARRANGEMENT" WHERE ...
    Ignore the rest of the statement. The name after FROM is your default view: V_FBNK_AA_ARRANGEMENT.
Why we do this: the DBA works in Oracle, not in T24. With the exact view name, the DBA can pull the view's script and see how each field is extracted from the XML. That extraction is what we will index.

Two more things JQL2SQL is useful for:

  • Run it with the real field and real criteria your code uses, for example JQL2SQL SELECT FBNK.EB.EMK.BNPL.SETTLEMENT.RPT.DETS WITH ORDER.ID EQ "A" "B". You'll see whether TAFJ generates IN (...) or a chain of ORs, and which view column it filters on.
  • Other examples from our environment: 
    JQL2SQL COUNT FBNK.EB.EMKAN.MERCHANT WITH @ID EQ "2121" "1212"
-> SELECT COUNT(RECID) FROM "V_FBNK_EB_EMKAN_MERCHANT" WHERE (RECID = '2121' or RECID = '1212')
    Notice that @ID becomes the view's RECID column. The view passes RECID straight through from the table (SELECT a.RECID …), without any XML extraction, and RECID is the table's primary key. That's why selecting by @ID is always fast and never needs an extra index.

6. Step 2: read the view script and find your field's expression

Give the view name to the DBA, or run this yourself if you have access:

SET LONG 1000000
SELECT DBMS_METADATA.GET_DDL('VIEW', 'V_FBNK_AA_ARRANGEMENT', 'TXN_ADMIN') FROM dual;

In the output, find the line for your field. For ORDER.ID on RPT.DETS:

,XMLCast(XMLQuery('/row/c4[position()=1]' PASSING a.XMLRECORD RETURNING CONTENT) AS VARCHAR(4000)) "ORDER_ID"

Check it against STANDARD.SELECTION for the table:

STANDARD.SELECTIONValueMust match in the view
SYS.FIELD.NAMEORDER.IDColumn alias "ORDER_ID"
SYS.FIELD.NO4/row/c4
SYS.SINGLE.MULTS (single value)[position()=1] takes value 1, which is the only value
Copy the expression exactly. Oracle uses a function-based index only when the query's expression is identical to the indexed one: the same XPath, the same [position()=1] and the same VARCHAR(4000). A small difference (c4[1] instead of c4[position()=1], or VARCHAR2(100) instead of 4000) can mean the index exists but is never used.

7. Step 3: create the function-based index

What a function-based index is

A normal index stores the values of a column. A function-based index stores the result of an expression. Oracle runs the expression once for every row when the index is built, then once for each row that is inserted or updated. It keeps the results in a sorted B-tree, each pointing back to its row.

Without index: every query

for each of 250,000 rows:
   open XMLRECORD
   find <c4>
   compare with 'X'
→ full table scan, minutes

With function-based index

index (sorted once, kept current):
  ORD-A → row 1, row 2
  ORD-B → row 3
  ...
query 'ORD-A' → jump to it → 2 rows
→ index range scan, milliseconds

The XML parsing moves from every selection to once per write.

Template

CREATE INDEX TXN_ADMIN.IX_<TABLE_SHORT>_<FIELD>_FBI
  ON TXN_ADMIN.<PHYSICAL_TABLE>
  (XMLCAST(
     XMLQUERY('/row/c<N>[position()=1]' PASSING XMLRECORD RETURNING CONTENT)
     AS VARCHAR2(4000)))          -- same path and length as the view
  TABLESPACE TXN_DATA
  ONLINE;                         -- T24 can keep writing during the build

EXEC DBMS_STATS.GATHER_TABLE_STATS('TXN_ADMIN', '<PHYSICAL_TABLE>', cascade => TRUE);

Real example (RPT.DETS, ORDER.ID)

CREATE INDEX TXN_ADMIN.IX_RPTDETS_ORDER_ID_FBI
  ON TXN_ADMIN.FBNK_EB_EMK_BNPL_SETTLEMENT_RPT_DETS
  (XMLCAST(
     XMLQUERY('/row/c4[position()=1]' PASSING XMLRECORD RETURNING CONTENT)
     AS VARCHAR2(4000)))
  TABLESPACE TXN_DATA ONLINE;

EXEC DBMS_STATS.GATHER_TABLE_STATS('TXN_ADMIN','FBNK_EB_EMK_BNPL_SETTLEMENT_RPT_DETS', cascade => TRUE);

What each part means

PartMeaning
CREATE INDEX (not UNIQUE)Duplicate values are allowed. Several records can share one value, for example several det records per order. Never use UNIQUE on a T24 field index.
XMLQUERY('/row/c4[position()=1]' PASSING XMLRECORD …)Opens the record's XML and takes the first <c4> element.
XMLCAST(… AS VARCHAR2(4000))Turns that XML element into plain text. A missing field becomes NULL.
TABLESPACE TXN_DATAWhere the index is stored. Ask the DBA whether indexes go in a separate tablespace.
ONLINEWrites to the table continue while the index builds. The build takes the same time or a little longer, with only two very short locks, at the start and the end. Needs Oracle Enterprise Edition.
GATHER_TABLE_STATS … cascade => TRUERefreshes the statistics the optimizer uses to choose between an index and a full scan. It only reads the table and takes no locks.

Why this method fits T24

  • No code change and no change to any T24/TAFJ object. The view, the table structure and STANDARD.SELECTION stay as they are.
  • Survives STANDARD.SELECTION rebuilds. A rebuild regenerates the view only. The index belongs to the table, and the regenerated view produces the same expression, so the index is still used.
  • Always up to date. Oracle maintains it on every write, in the same transaction.
  • Identical results. It is the view's own expression, so selections return exactly the same records, only faster.
  • Rollback is one line: DROP INDEX …;

8. Step 4: prove the index is used (EXPLAIN PLAN)

Creating an index doesn't guarantee Oracle will use it. Always check the execution plan against the view, using the same kind of SQL that JQL2SQL showed you:

EXPLAIN PLAN FOR
  SELECT RECID FROM TXN_ADMIN.V_FBNK_EB_EMK_BNPL_SETTLEMENT_RPT_DETS
  WHERE ("ORDER_ID" = '20251116-WF-1794147449223390-BNPL'
      OR "ORDER_ID" = '20251116-WF-1794148001299799-BNPL'
      OR "ORDER_ID" = '20251116-WF-1794208317899419-BNPL');

SELECT * FROM TABLE(DBMS_XPLAN.DISPLAY);
Before: full table scan 
TABLE ACCESS FULL
  FBNK_EB_EMK_BNPL_SETTLEMENT_RPT_DETS
  Cost 482
filter(EXTRACTVALUE(...'/row/c4[1]'...)='...' OR ...)
Note: Unoptimized XML construct detected
Every row's XML is parsed and compared.
After: index range scan 
INLIST ITERATOR
 TABLE ACCESS BY INDEX ROWID BATCHED
  INDEX RANGE SCAN IX_RPTDETS_ORDER_ID_FBI
  Cost 1
access(XMLQUERYVAL('/row/c4[position()=1]'...)='...' OR ...)
Oracle matched the view's expression to the index.

What to look for:

  • INDEX RANGE SCAN with your index name means it worked.
  • TABLE ACCESS FULL means the index isn't being used. Re-check that your expression is identical to the view's (section 6).
  • The predicate starts with access(...), not filter(...). "Access" means Oracle uses the index to find rows. "Filter" means it reads rows and then throws some away.

Then, still in SIT:

  1. Rebuild the table's STANDARD.SELECTION and run the EXPLAIN PLAN again. It must still show the index.
  2. Input and authorise a record of that table in T24, to confirm writes still work.
  3. Run the actual JQL or service and compare the timing.

9. Approaches that look tempting but don't work

ApproachWhy we rejected it
Virtual column + index + editing the view to read the new columnThe plan was fast, but rebuilding STANDARD.SELECTION regenerated the view and wiped the edit (confirmed in SIT). The index then stopped being used, without any error.
T24 alternate index (SYS.ALT.INDEX = Y on STANDARD.SELECTION)On our system field, T24 rejected SYS.ALT.INDEX, SYS.IDX.FILE and SYS.INDEX.NULLS with "You cannot edit this field".
Materialized view + indexTAFJ always queries its own default view, never a materialized view, so code changes would be needed. The data is also only as fresh as the last refresh, so new records would be missed.
Index on a different expression (for example EXTRACTVALUE(...) or a different length)Oracle uses a function-based index only when the expression matches the one TAFJ's view uses.

10. When to index, and when not to

Good candidates
  • Fields used in WITH … EQ … by services, enquiries or COB jobs that are slow.
  • Selective fields, where each value matches few records (order IDs, references, account numbers).
  • Single-value fields (SYS.SINGLE.MULT = S).
  • Fields written once and rarely changed.
Think twice
  • Multi-value fields: [position()=1] indexes only the first value, so a search on value 2 or later won't use it.
  • Fields with very few distinct values (a status with three values on its own). Combine it with another field in a composite index instead.
  • Tables that are written very heavily and rarely selected. Every index adds a small cost to each insert.
  • Selections by @ID. These already use the RECID primary key.
Cost to writes: T24 rewrites the whole XMLRECORD on every update, so Oracle re-evaluates the indexed expression on each write. If the field's value didn't change, it doesn't touch the index. For one row the extra cost is negligible compared with the cost of a T24 write. On write-heavy tables, test a bulk process in SIT before and after creating the index.

11. Case study: a nightly service that silently skipped work

This is a real issue we fixed. You don't need to know the business behind it: the pattern can happen on any project with a large custom table.

The setup

  • A nightly service (a multi-threaded T24 service) processes a list of parent records. For each parent, it loads that parent's child records from a custom detail table and updates them.
  • The children are loaded with a JQL selection on a field that points to their parent, a reference field (in our case named ORDER.ID) stored inside XMLRECORD as <c4>: 
    SELECT <DETAIL.TABLE> WITH ORDER.ID EQ "id1" "id2" "id3" ...
  • The service selects up to 500 parent IDs in one statement to cut down the number of database calls.

The symptom

After each run, some parents were never processed. Their records stayed in their original status, and nothing in the service output explained why. Other parents in the same run were processed normally.

Why it couldn't be reproduced in SIT

We loaded SIT with a heavy case (about 1,300 child records for a single parent) and the service worked perfectly. The difference was the size of the detail table:

SITProduction
Records in the detail table~11,000~250,000
Work per selection, without an indexSmall~23 times more

Without an index, a selection on a field inside the XML parses every record in the table, so it gets slower as the whole table grows, not just as the data you're selecting grows. SIT was simply too small to show the problem.

How we found it

We deployed a version of the service with detailed file logging: a timestamp before and after every database call. The production logs showed exactly where it stopped:

IDs in one selectionTime for that one SELECTWhat happened next
50~21 minutesTAFJERR-1110: Session Logoff. The session was ended, every later call failed, and nothing was written for that parent.
195~60 minutes

Reading the same records by @ID took under a second, so the database itself was healthy. Only the selection by a field inside the XML was slow.

The fix

  1. Found the view with JQL2SQL (section 5).
  2. Copied the ORDER_ID expression from the view script (section 6).
  3. Created a function-based index on exactly that expression (section 7). There was no code change and no change to T24 objects.
  4. Proved it with EXPLAIN PLAN (section 8): a TABLE ACCESS FULL with cost 482 became an INDEX RANGE SCAN with cost 1.
Lessons you can reuse on any project:
  • "Works in SIT, fails in production" combined with "it depends on data volume" usually points to a missing index.
  • A selection that is too slow doesn't always fail loudly. The session can be ended, and the work is silently skipped. Log the timing of database calls in batch services.
  • Big EQ "a" "b" "c"… lists make an unindexed selection worse, because every row is compared against every value.
  • Before blaming the code, run JQL2SQL and EXPLAIN PLAN. One TABLE ACCESS FULL on a large table explains a lot.

12. One-page checklist

  1. Identify the slow selection: the JQL, the table and the field.
  2. In STANDARD.SELECTION, note the field's SYS.FIELD.NO (the cN) and check that it's single-valued.
  3. In DBTools, run JQL2SQL COUNT FBNK.<TABLE> WITH <ANY.FIELD> EQ "x" and note the view name after FROM.
  4. Get the view DDL (DBMS_METADATA.GET_DDL) and copy the field's exact expression.
  5. In SIT, run EXPLAIN PLAN against the view to record the "before" plan.
  6. Create the function-based index with the identical expression, ONLINE, then gather statistics.
  7. Run EXPLAIN PLAN again. It must show INDEX RANGE SCAN on your index.
  8. Rebuild STANDARD.SELECTION and check the plan again. Input and authorise one record.
  9. Raise a ticket with the before and after plans, then deploy to production outside COB and service windows.
  10. Rollback if needed: DROP INDEX <name>;
